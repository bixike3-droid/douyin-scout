# 源镜的 12-Factor Agents 优化评估

评估日期：2026-10-20。范围：当前 `douyin-scout` 工作区中的对话、工具、固定协作流程与持久化实现；MediaCrawler 未纳入本次评估。下文保留修改前的评估，实施进展单独记录。

结论：沿用现有 Python / SQLite / PySide6 架构，先修复长期记忆，再补工具输入校验和预算退出，随后将普通对话接到可恢复的执行记录。已有固定流程的数据快照、成果交接和恢复机制应继续复用。

## 已实施（2026-10-20）

- 长期记忆改用真实消息 ID 游标，增量合并旧摘要与新消息；未压缩的发言保留。压缩失败不推进游标，乱序完成的摘要不能覆盖更新的进度。
- 工具入口统一检查 JSON、必填字段、类型、枚举及已声明的范围，坏参数不会触发确认或执行。失败返回错误码与可重试标志，未知工具也记审计。
- 普通对话限制实际工具尝试次数和模型客户端调用次数，委派共享模型额度；预留关闭工具的总结，无法总结时按已保存结果交付部分成果。
- 普通对话的执行意图、确认决定、完整结果及额度持久化。重新打开后能继续；已完成结果直接重用，已拒绝的相同请求不再询问；过期确认不会执行。写操作执行中断且无法确认结果时标记待核对。
- 桌面新增普通对话任务卡、执行记录和继续入口，沿用账号执行锁。
- 模型调用记录覆盖派单、普通回复、总结、摘要、委派和固定流程；保存提示词哈希、输入摘要、用量、耗时与重试次数。普通回复恢复模型名和聚合用量保存。
- 新迁移 `0021_agent_execution.sql` 仅新增表；旧摘要仍保留，游标从原文重新建立。

角色专用上下文构建器、带证据引用的委派协议和热点混合流程仍属后续优化；本次先完成可靠性与恢复基础。

实施验证：392 项非界面测试通过；34 项工作台测试、2 项固定流程界面测试、2 项普通对话恢复界面测试通过，共 430 项。桌面离屏启动自检与源码编译检查通过。未使用真实账号或在线模型执行采集验收。

## 原始资料与适用方式

[HumanLayer 原始项目](https://github.com/humanlayer/12-factor-agents)是一组工程原则。作者主张将小块的模型能力融入已有软件；对源镜的启发是让程序明确管理任务、证据、权限和恢复边界。

重点参考：[上下文管理](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-03-own-your-context-window.md)、[结构化工具输出](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-04-tools-are-structured-outputs.md)、[统一状态](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-05-unify-execution-state.md)、[启动与恢复](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-06-launch-pause-resume.md)、[控制流程](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-08-own-your-control-flow.md)、[错误反馈](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-09-compact-errors.md)、[职责收敛](https://github.com/humanlayer/12-factor-agents/blob/main/content/factor-10-small-focused-agents.md)。下文的优先级、表设计和验收条件是结合本项目提出的方案。

## 十二项原则对照

| 原则 | 当前实现 | 项目建议 |
|---|---|---|
| 1 自然语言转工具调用 | 调度器、成员工具循环均已实现 | 保留；把执行前校验补到代码入口 |
| 2 自主管理提示词 | 提示词在源码中；方案报告保存系统提示词 | 普通对话、分析阶段和委派补提示词版本及输入摘要 |
| 3 自主管理上下文 | 历史限长、会话摘要、企业摘要、冻结快照 | 修复摘要更新；按角色挑选证据并统一预算 |
| 4 工具是结构化输出 | ToolSpec 定义 schema，执行器管理权限 | 增加运行时校验与统一结果结构 |
| 5 统一执行与业务状态 | 固定流程有 run / step / artifact；普通对话主要依赖内存 | 共用任务身份和持久化工具结果，界面从执行记录读取状态 |
| 6 简单的启动、暂停、恢复接口 | 固定流程已有继续与重做 | 普通工具对话、等待确认也支持重新打开后恢复 |
| 7 用工具联系用户 | 确认卡、ConfirmationBroker 已接通 | 将待确认请求和决定持久化，并绑定具体参数 |
| 8 自主管理控制流 | 固定模板、最多 6 轮、取消处理 | 区分模型轮数和工具次数，预算耗尽时保存部分成果 |
| 9 将错误压缩反馈给模型 | 工具失败回喂；阶段输出可修正一次 | 增加错误码、可重试标志和重复失败抑制 |
| 10 小而专注的成员 | 七个角色；固定阶段职责清晰 | 优先完善有证据的交接；委派按需开放受限工具 |
| 11 多入口触发 | 桌面操作和对话已复用部分业务能力 | 先统一内部 start / resume / cancel / get 接口；额外入口按需求增加 |
| 12 无状态归约器 | 执行函数仍依赖临时上下文属性和内存循环 | 可逐步拆出由持久状态决定下一动作的纯函数；外部效果仍由执行器处理 |

第 12 项的具体拆法是本项目设计建议，无需先引入完整的事件溯源体系。

## 已有基础

- `analyze/workflow.py` 用固定模板管理受众、作品和方案任务，分析阶段使用同一冻结快照，策略接收已保存的前序成果。
- `store/workflow.py` 已管理任务、步骤、成果与检查点；`WorkflowLease` 限制同账号重复运行。阶段成果、会话消息及方案关联有事务边界。
- 引用编号和结构会在阶段交付前校验，无效输出可修正一次；缺少数据时跳过对应阶段并标注部分完成。
- `tools/registry.py` 在执行时重新校验成员权限，采集等工具有确认流程。网页内容已有归档机制，可以继续扩展成可追踪的证据引用。

## P0：先修复三处可以独立交付的问题

### 1. 长会话摘要会停止更新，并可能遗失早期约束

位置：`store/conversation.py:36`、`analyze/conversation.py:245`。

`history()` 最多返回最近 20 条、16000 字的完整发言；`_maybe_summarize()` 却把这个窗口的长度当成累计进度。窗口达到 20 后，长度不再增加，更新阈值无法再次满足。它重建摘要时也没有传入上一版摘要；而正常回复只保留最近 8 条原文，较早但尚未摘要的内容存在缺失区间。

离线复现：逐条新增 60 条短消息，每条后检查摘要。结果为 `saved_messages=60, visible_history=20, summary_calls=2, stored_turns=20`。

建议：

- 用 `covered_message_id` 记录已压缩到的真实消息边界，与发给模型的历史窗口分开。
- 读取“上一版摘要 + 尚未覆盖的旧消息”做增量压缩；摘要及游标在一个事务中提交。
- 构建上下文时保留尚未压缩的发言；超预算时先完成压缩，避免直接只取最近 8 条。
- 失败、取消和未完成消息继续排除在事实记忆之外。

验收：连续至少 60 条消息，早期确认的约束和近期变更都能保留；摘要失败不推进游标；重启后继续增长；长文本触发字数上限时也不丢进度。

### 2. 工具 schema 尚未成为统一的执行约束

位置：`tools/registry.py:57`、`analyze/conversation.py:202`。

schema 当前提供给模型，但 `execute()` 在调用 handler 前没有统一验证。部分 handler 自行检查枚举或做数值钳制，覆盖程度不一致。普通对话里，无法解析的参数还会变成 `{}`，可能让有默认值的操作继续执行。

离线复现：注册要求整数 `count` 的假工具，传入字符串 `not-an-integer`，handler 仍被执行并返回成功。这证明执行入口缺少统一保证，不代表所有现有工具都允许该参数错误通过。

建议：

- 在用户确认和 handler 执行前，校验 object、required、类型、enum、长度与范围等项目实际使用的 schema 约束。
- 参数 JSON 无效时返回 `INVALID_ARGUMENTS`，附具体字段问题；不要静默替换为空参数。
- 结果统一为 `ok / code / summary / retryable / data或result_ref / partial`，保留完整审计。
- 未知工具同样记录审计；当前未知工具路径会在 `_audit()` 前返回。

验收：错类型、缺字段、非法枚举、坏 JSON 均不触发确认卡或 handler；错误反馈给模型后，修正参数可以正常执行。

### 3. 工具预算耗尽会把已经完成的动作变成整轮失败

位置：`analyze/conversation.py:35`、`:177`、`:217`。

`MAX_TOOL_STEPS=6` 实际限制模型循环次数。一轮可返回多次调用；第 6 轮执行完工具后，没有剩余轮次让模型整理结果，于是走“模型没有返回可用回复”的异常路径。

离线复现：假模型每轮返回两个只读假工具调用，共 6 次模型调用、12 次工具执行，最终会话标记为失败。实际完成动作的审计仍在，但本轮用户消息被排除出后续成功历史，工具结果也没有进入持久的对话上下文。

建议：

- 分别限制模型调用次数、工具执行次数、连续同类错误和总耗时；每次具体执行前扣减工具额度。
- 循环将尽时转入关闭工具的总结调用，并预留对应预算。
- 总结也失败时，用确定性文本交付已完成动作、已有结果和未完成部分，标记 `partial`。
- 记录 `(tool_id, canonical_args, error_code)`；重复失败达到阈值后由程序终止或改变处理方式。

验收：最后一轮仍有工具调用、多调用批次、反复相同失败、总结服务不可用四类场景，均不突破预算，且准确保留已完成的动作。

## P1：将普通对话补成可恢复的任务

位置：`analyze/conversation.py:110`、`tools/registry.py:93`、`tools/confirm.py:27`、`store/workflow.py`。

普通对话的 `convo`、模型选中的调用和完整工具结果主要在内存中。`tool_calls` 当前在操作结束后记录参数、状态和简短说明，缺少提供商调用 ID、执行前状态与完整结果引用；确认等待者是内存里的 Future。固定流程能恢复到阶段，普通对话尚不能恢复到某次工具调用。

建议在既有存储层渐进扩展：

1. 每轮有稳定的 `run_id` 和 `user_message_id`；每次调用有稳定的 `call_id`，并关联 run / step / provider_call_id。
2. 模型选择工具后，先提交工具名、规范化参数、参数摘要及 `selected` 状态。
3. 需要确认时持久化 `request_id / args_hash / expires_at / decision`，进入 `waiting` 后退出执行；用户决定通过统一 resume 入口推进。
4. 执行前记录 `running`；完成后保存结构化结果或结果引用，再继续模型决策。
5. 从同一份执行记录生成任务卡、审计和恢复上下文。沿用已有的账号与会话校验、文件锁、阶段成果事务，避免另外维护一份互相矛盾的运行状态。

确认只对特定调用和参数有效，参数变化后不能复用。过期的 pending 决定不自动当作允许；已经拒绝的相同调用不因重启而重新询问。

浏览器操作与 SQLite 无法共同提交原子事务。如果进程在动作完成、结果落库前退出，状态应标为待核对，先检查实际效果或底层任务状态。只有具备幂等保证或可确认未执行的操作才能自动重试。

验收：分别在选择后、等待确认中、执行中、结果提交后强制中断再恢复；已完成动作不重复，拒绝不丢失，无法确认是否执行的动作明确进入待核对状态。

## P1：让证据和使用量可追踪

### 角色上下文与交接

位置：`analyze/conversation.py:71`、`analyze/workflow.py:260`、`tools/delegate.py:17`。

普通成员共享同类企业摘要，靠逐项及总字符截断控制长度；固定分析阶段都接收完整快照；委派只有一次无工具调用，任务文本截到 800 字。需要实时数据的委派因此无法自行查证，交接也没有稳定的证据引用。

建议增加 `ContextBuilder`：按成员职责、任务范围和预算选择证据；保留来源、采集时间、样本范围、未知值及证据 ID。完整内容保存在本地，通过引用按需读取。首次可用保守的字符预算，记录实际 token 后再校准估算。

交接使用 `goal / scope / evidence_refs / constraints / expected_output`。只有确实需要查证的委派才开放角色白名单工具，并设置少量调用额度、共享总预算和一层深度限制。仍然由程序串行控制浏览器采集。

热点与本机分析混合请求目前常被 `needs_live_tools()` 保留在普通对话。后续可为方案流程增加可选的热点证据阶段，再冻结成同一份输入；先做明确模板，减少临时自由协调。

验收：各角色输入只包含必要证据；截断不丢失范围与时间；网页事实、分析假设及历史建议有明确区别；混合任务能追溯每项结论来自哪份快照或网页。

### 模型记录与回归评估

位置：`analyze/conversation.py:221`、`store/conversation.py:25`、`store/workflow.py:102`。

普通对话保存 assistant 时没有传 `reply`。离线复现中，假回复自带模型名、123 个输入 token、45 个输出 token 和 67ms，数据库却记录为空模型和全零使用量。固定阶段成果有 usage 字段，但路由、摘要和委派也需要计入整项任务的消耗。

建议用统一模型调用记录保存 `run_id / purpose / agent / model / prompt_version / input_digest / usage / duration / retries / status`，覆盖路由、工具循环、总结、修复和委派。各次调用分别记录，再聚合成任务成本，避免只统计最后一次回复。

沿用源码提示词，补版本或哈希，无需为了本次优化引入远程提示词平台。用固定合成样本评估路由误判、长期约束保留、无效引用拒绝、拒绝后重复调用、部分交付和恢复行为；成本改进需用真实记录验证，当前不承诺固定降幅。

## 建议交付顺序

| 批次 | 可独立交付的范围 | 可观察结果 |
|---|---|---|
| A | 摘要游标、增量压缩、未覆盖历史保留 | 长对话继续记住早期约束与后续变更 |
| B | 参数校验、错误结构、工具次数预算、部分交付 | 坏参数不执行，额度耗尽仍有准确结果 |
| C | 普通对话执行记录、结果持久化、确认恢复 | 重新打开后能明确继续，避免盲目重复动作 |
| D | 角色 ContextBuilder、结构化交接、统一调用遥测 | 输入更聚焦，结论和模型消耗可追溯 |

每批完成对应回归后再扩大范围。源镜当前的单机使用场景不需要为了符合原则引入分布式调度或额外服务。
